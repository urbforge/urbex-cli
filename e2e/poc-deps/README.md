# PoC, dependencies between Komodo Stacks

A block is a `compose.yaml` that Komodo deploys as one Stack, with its own
services. Compose orders the services inside a block. Nothing orders two
blocks, and `uses` between applications needs that.

This PoC takes the graph of six blocks Teg proposed and orders them with what
Komodo already has, before anything is built in the CLI. The first round, on
three blocks, showed that a Procedure with a stage per block does not order
anything (`DeployStack` returns before the services are healthy), and that a
wait placed in the Stack does.

```
dns -> gitea -> keycloak -> photos
       gitea -> acme-db ---+
       keycloak -----------+-> acme-api
```

Each block's `app` listens at once and becomes healthy a few seconds later,
so "the container runs", "the port answers" and "it can take calls" are
three different moments. A consumer that starts too early finds `/ready`
missing and exits, as an application does when its dependency is not there.
`keycloak` has a `db` service too, and `photos` has no healthcheck, to see
what "ready" means without one.

## Run it

It needs only podman, and takes about ten minutes the first time (it pulls
Komodo and busybox inside the machine).

```sh
e2e/poc-deps/run.sh --clean                  # Komodo 2.3.4, all the tests
e2e/poc-deps/run.sh --tests G1,G3,G5         # some of them
```

The machine is a privileged Debian container with systemd and Docker, like
the one the e2e uses for an LXC. Komodo Core and Periphery run in it as they
do on urbex's Komodo LXC. Credentials are generated in the machine and never
written in the repository. Use `--clean` when the Komodo version changes
(`--komodo-version`).

## The tests

| Test | What orders the blocks |
|---|---|
| G1 | A `wait` service in each block, probing the application's `/ready`, ignored by Komodo with `ignore_services`. |
| G2 | The same, probing only the TCP port (ready, not healthy). |
| G3 | A driver outside the Stacks, in topological order, reading health from `ListStackServices`. |
| G4 | G1 with `acme-db` failing and a 30 s timeout. Only `acme-api` should stay blocked. |
| G5 | G3 with `acme-db` failing and a 30 s timeout. |

The compose files are generated by `inside/graph.py`.

## What it measures

For each test, from a monitor that looks at the containers every second.

- Whether each block started after the blocks it needs were healthy.
- How long the deploys took to return and how long everything took to be healthy.
- Restarts, and the lines that say a dependency was not ready.
- In the failure tests, whether the blocks that depend on the failed one
  never started and the others did.
- What Komodo says about each Stack (`running`, `unhealthy`, `down`), and the
  first answer of `ListStackServices` for each block.
- What Periphery has (`bash`, `curl`, `nc`, `python3`, the Compose version).

## Results

`results/<komodo version>/summary.md` has one row per test. Each test also has
a `.md` with a row per block and its timeline, and a `.g.json` with everything.
The `periphery-tools.txt` file lists what the Periphery image has. Send
`summary.md` and the `.md` of any failed test back.

## What it does not cover

- Several hosts. All the blocks run on one Docker, on a shared network, so
  the names resolve as the internal DNS names will. Two machines and two
  Peripheries are a second phase.
- A reboot. No construct covers it, and the first round measured the
  restart policy alone (about 30 s to be healthy again).
- Proxmox, Technitium and the GitOps repository.

## Known unknowns, to look at first when a test fails

- The shape of `ListStackServices`. The driver looks for `(healthy)` or `Up`
  in each service's JSON.
- Whether `ignore_services` also hides the exited `wait` from the Stack's
  state, and what the exited one-shot does to it.
